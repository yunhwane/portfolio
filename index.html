문제
리뷰를 랜덤으로 조회하도록 기획돼 있어, 인덱스를 타지 못하고 매번 풀스캔이 발생했습니다.
해결
랜덤 조회는 인덱스를 태울 방법이 없어 쿼리 튜닝으로는 한계가 있다고 보고, 기획을 바꾸는 쪽으로 접근했습니다. 마침 관심항목 설정은 사용자가 설정만 할 뿐 어디에도 쓰이지 않는 기능이었는데, 이를 리뷰 조회에 연결해 성능 문제와 방치된 기능을 함께 해소했습니다.
관심항목과 리뷰를 잇는 가중치 테이블을 두고, 카테고리별 우선순위 컬럼을 가중치로 삼아 정렬하도록 바꿨습니다. 항목 매칭에는 pg_trgm 기반 인덱스를 설계해, 랜덤 정렬로 풀스캔하던 조회를 인덱스를 타는 조회로 전환했습니다. 페이지네이션도 offset 기반에서 cursor 기반으로 바꿨습니다.
결과
풀스캔이 사라지고, 개발 환경 4만 건 기준으로 조회 시간이 1.422초에서 0.401초로 72% 줄었습니다. 사내 슬로우 쿼리 기준인 1초 아래로 내려왔습니다.
설정만 하고 쓰이지 않던 관심항목이 실제 리뷰 조회에 반영되기 시작했습니다.

공통 코드·카테고리 2-Tier 캐시

Local + Redis
문제
각 서버 인스턴스가 공통 코드·카테고리를 로컬 캐시로만 들고 있었습니다. 스케일아웃하면서 인스턴스마다 같은 데이터가 중복 적재됐고, 한 곳에서 수정해도 다른 인스턴스는 옛 데이터를 그대로 들고 있어 정합성이 깨졌습니다.
해결
Redis를 상위 캐시로 두고 Caffeine 로컬 캐시가 Redis만 바라보도록 설계했습니다. 수정·삭제 시 Redis Pub/Sub로 전 인스턴스의 로컬 캐시를 즉시 무효화해 정합성을 맞췄습니다.
다만 Pub/Sub은 메시지를 놓친 인스턴스에 재전송하지 않습니다. 그래서 TTL을 1~2분으로 짧게 둬 이벤트가 유실돼도 오래 어긋나지 않게 하고, 무효화를 직접 호출할 수 있는 API를 별도로 두어 이중으로 방어했습니다. TTL은 정합성 수단이 아니라 안전장치로만 쓴 셈입니다.
메모리 중복과 조회 정합성 사이의 트레이드오프를 이 구조로 관리했습니다.
결과
공통 코드·카테고리 조회에서 DB 접근이 사라져 슬로우 쿼리가 해소됐고, 스케일아웃 환경에서도 인스턴스 간 정합성과 일관된 응답을 확보했습니다.
Redis Caffeine

결제 흐름 설계

문제
결제 코드가 두 서버에 나뉘어 있었고, 망취소가 구현돼 있지 않았습니다. 결제 이후의 후속 처리가 실패해도 로그가 남지 않아 무엇이 어디서 멈췄는지 추적할 수 없었습니다.
해결
흩어져 있던 결제 코드를 결제 서버로 모으고, KG이니시스 연동의 승인 흐름은 동기로 처리했습니다. 돈이 오가는 흐름은 결과를 즉시 확정해야 하고, 승인은 성공했는데 우리 쪽 반영이 실패하면 망취소로 되돌려야 하기 때문입니다.
결제 수단별로 흐름이 갈립니다. 카드는 PG 인증 결과 콜백을 받은 뒤 승인 요청부터 결과 확정까지를 한 흐름에서 처리하고, 구독형은 빌링키로 승인 API를 직접 호출합니다. 가상계좌는 발급과 입금 시점이 분리돼 입금 통보가 웹훅으로 뒤늦게 도착하므로, 그 지점부터 별도 흐름으로 다뤘습니다.
결제 이후의 알림·상태 변경·후속 처리는 이벤트로 분리해 결제 모듈이 결제 자체에만 책임지게 했고, 주문형과 구독형의 흐름 차이에 맞춰 이벤트 구조를 설계했습니다.
메시지 브로커는 Kafka를 골랐습니다. 이미 이벤트 메시지에 Kafka를 쓰고 있어 새 인프라를 들이지 않고 기존 운영 경험을 그대로 쓸 수 있었습니다.
결제 트랜잭션과 이벤트 발행의 일관성은 트랜잭션 아웃박스 패턴으로 맞췄습니다. 결제는 커밋됐는데 발행이 실패하면 후속 처리가 조용히 유실되므로, 이벤트를 결제와 같은 트랜잭션 안에서 아웃박스 테이블에 남기고 별도 프로세스가 이 테이블을 폴링해 Kafka로 발행하도록 했습니다. 발행 전 이벤트가 DB에 남아 있어 유실이 없고, 실패한 이벤트도 기록으로 추적할 수 있습니다.
결과
두 서버에 나뉘어 있던 결제 코드가 결제 서버 하나로 모였습니다. 결제 흐름을 운영팀이 대시보드에서 추적할 수 있게 되면서, 결제가 실패한 건은 곧바로 환불 처리할 수 있게 됐습니다.

예약 발행

문제
네이버·티스토리·인스타그램·페이스북에 게시글을 예약 발행하는 기능을 Kafka 기반 비동기로 처리했는데, 같은 메시지가 중복으로 들어오는 경우가 있었습니다. 스케일아웃된 환경이라 중복 메시지를 그대로 처리하면 같은 글이 여러 번 발행될 수 있었습니다.
원인
Kafka는 at-least-once 전달을 보장하기 때문에 리밸런싱이나 재처리 과정에서 중복 메시지가 나오는 것이 정상 동작 범위였습니다. 중복을 막을 책임은 소비 측에 있었습니다.
해결
중복이 생길 수 있는 층위가 둘이라 각각 막았습니다. 인스턴스 사이에서는 예약 건 ID를 키로 한 Redis 분산 락으로 한 인스턴스만 집도록 하고, 인스턴스 안에서는 세마포어로 같은 메시지가 여러 스레드에 동시에 잡히지 않게 했습니다.
다만 락은 동시 실행만 막습니다. 락이 풀린 뒤 같은 메시지가 다시 들어오는 경우까지 거르려면 상태를 봐야 하므로, 락을 잡은 뒤 이미 발행됐는지를 확인하고 처리 여부를 결정했습니다.
결과
스케일아웃 환경에서도 같은 글이 중복 발행되지 않게 됐습니다.
Kafka Redis

해결
전부를 덮는 대신 실패 비용이 큰 도메인부터 시작했습니다. 원고 컨펌은 광고주에게 원고가 직접 전송되고 결제는 돈이 걸려 있어, 여기서 나는 버그의 대가가 가장 컸습니다.
작성 기준을 정했습니다. 단위 테스트는 비즈니스 로직과 상태 변경만 도메인 테스트로 다루고, 인수 테스트는 사용자 시나리오 전체를 검증합니다 — 비밀번호 변경이라면 로그인부터 변경 실패·성공까지요.
검증 방식은 Fake로 통일했습니다. 모킹은 어떤 호출이 일어났는지를 볼 때 쓰는 도구인 반면 Fake는 상태 검증에 맞는데, 이 서비스는 상태 변경이 잦고 거기서 나는 버그의 위험이 가장 컸습니다. 그래서 상태를 실제로 들고 있는 Fake 객체를 Java 코드로 직접 작성하는 것을 컨벤션으로 삼았습니다.
JUnit 4로 테스트 400여 개를 작성하고, CI에 인수 테스트까지 포함시켰습니다.
결과
새로 합류한 팀원이 원고 제출 시 상태 변경 로직을 수정하다 만든 사이드 이펙트를 테스트가 잡아냈습니다.

이미지 서버 개발

문제
5개 API 서버에 이미지 업로드·다운로드 로직이 중복돼 있었고, multipart로 동기 처리하는 구조라 이미지 전송이 끝날 때까지 API 서버가 묶여 있었습니다.
해결
인플루언서가 한 번에 15장 이상, 많게는 30~40장의 고화질 사진을 올리는 서비스였습니다. multipart 동기 업로드를 유지하면 업로드가 끝날 때까지 API 서버가 묶여 성능과 업로드 경험이 함께 나빠질 것으로 판단했습니다.
클라이언트가 presigned URL을 발급받아 S3에 직접 업로드하도록 바꿔, 이미지 트래픽이 API 서버를 거치지 않게 했습니다.
리사이즈는 요청 시점에 변환하지 않고, S3 업로드 이벤트로 Lambda를 트리거해 미리 생성한 뒤 별도로 저장했습니다. 5개 클라이언트가 모두 같은 규격을 사용하고 있어 요청마다 변환할 이유가 없다고 판단했습니다.
결과
이미지 트래픽이 API 서버를 거치지 않게 되면서, 30~40장을 한 번에 올리는 동안에도 API 서버가 업로드에 묶이지 않게 됐습니다. 5개 서버에 흩어져 있던 업로드·다운로드 로직도 presigned URL 발급으로 일원화했습니다.
